# 调研章程：个人即协同网络（2026-11-08）

> 本文件是**跨主题对齐修正与调研框架**，不是产品方案、技术方案，也不是编译器产出的决策报告。

## 1. 对齐修正（推翻此前假设）

前三份技术调研报告（`zagenticopn` / `orca` / `herdr`）的 brief 里都写了同一个 ALIGNMENT ITEM：「假设 zj 的 job 是评估该项目在 ZOnePersonNetwork 中的采用形态（整体并入 / 单元能力复用 / 组合 / 仅参考 / 不采用）」。

**该假设错误，现予作废。** zj 明确的真实意图是：

- 在当前项目（ZOnePersonNetwork）**重新开发「个人即协同网络」这一产品方向**，ZAgenticOPN 是**参照物**，不是待采纳或待替换的候选；
- 目的是**吸取 ZAgenticOPN 开发时的两个教训**；
- **当下阶段只做调研**：掌握多个类似项目的**产品设计和技术设计**，之后才做总体产品方案与技术方案讨论。

因此后续所有调研的 decision frame、goals、options、criteria 必须重建，不得沿用「采用形态」框架。

## 2. 两个痛点（zj 口述，最高优先级来源）

1. 整个产品概念是明确的，但**它应该由哪些产品模块和功能构成是不清晰的**。
2. 大多数内容都需要**从 0 到 1 开发，工作量巨大**。
3. 两者叠加的后果：**zj 和 Coding Agents 的工作困在细节里**。

## 3. 根因假设（第一性原理推断，标注为待验证，不作为结论）

```text
缺产品模块地图
  → 无法把概念拆成有边界的功能单元
  → 无法判断哪些单元已有现成实现可复用
  → 默认全部自研（0→1 工作量巨大）
  → 实现细节反过来定义产品语义
  → 人与 Coding Agent 都沉到细节，讨论无法收敛到方案层
```

痛点 1 与痛点 2 不是两个独立问题，是同一条因果链的两端。因此调研的**第一产物应当是模块地图 + 每格的复用边界**，而不是「某项目能不能用」。

这里还有一个方法论缺口：前三份报告用的是 `technical-c4/v1` 的**能力组合矩阵**（产品语义 / 状态与上下文 / 身份与作用域 / 执行与沙箱 / 传输与 API / 可观测 / 部署 / 生命周期所有权）。那是**架构层维度**，回答的是「集成为谁负责」，**不等于产品模块地图**（「这个产品由哪些功能单元构成」）。痛点 1 正是缺后者。

## 4. 新的统一调研问题（替代「采用形态」）

对每一个类似项目，问同一组问题：

| 层 | 要回答什么 |
|---|---|
| 产品模块构成 | 系统由哪些用户可见的功能单元组成？每个模块的职责边界与对外契约是什么？ |
| 技术设计 | 每个模块的数据模型、状态机、协议/接口、持久化、隔离与安全、升级与版本偏斜、测试与验证方式 |
| 复用边界 | 每个模块是「可直接用 / 适配可用 / 必须自研」？依据是哪条 sealed Evidence？ |
| 组合顺序 | 模块间依赖关系是什么？最小可运行切片由哪几个模块组成？ |
| 人机分工 | 哪些决策必须 Human、哪些可交给 Coding Agent、边界用什么机制表达（避免困在细节） |
| 工作量信号 | 模块数、接口数、必须自研的比例、上游治理（能否贡献 / 是否只能 fork） |

**候选产品模块清单（草案，待 zj 校准，不是定稿）**：① 任务与工作项（Work Item / 状态机 / claim / handoff）② 协作拓扑与身份（人、Agent、设备、scope、成员）③ 会话与上下文（生命周期、上下文携带、恢复）④ 执行与工作区（隔离、编排、任务分配）⑤ 审批与人工介入（Human gate、干预记账）⑥ 结果与产物（产物、review、provenance、验收）⑦ 知识与记忆（事实沉淀、检索、复用）⑧ 可观测与回放（状态可视化、事件、诊断）⑨ 配置与策略（规则、skill、版本）⑩ 运行时与集成（安装、升级、host adapter、跨平台）。

## 5. 方法论调整（需要 zj 拍板的反驳点）

- **旧做法**：每个项目产出一份「采用决策报告」（推荐 / 拒绝 / 阶段退出）。与「掌握多个项目的产品设计」目标正交——产出 N 份文档，仍拼不出一张模块地图。
- **新做法**：**横向模块矩阵**作为统一 SoT，多个项目在同一张表里按同一组维度对齐；最终报告仍走 `zj-research` collect + `zj-tech-research-report` 编译器产出（`technical-c4/v1`），**不手写竞争版报告**。矩阵作为 brief criteria 与 IR `comparisons` / `metrics` 的输入。
- 证据规则不变：能力结论只认 commit-pinned sealed Evidence ID；非 sealed 一手阅读只用于风险与验证门；`unknown` ≠ `absent`；stars / topicMatch / README 长度不作能力分数；`unknownCriteria: []` 不等于证据充分。

**结论层作废不是因为证据错，而是 decision frame 变了**：原来问「要不要用这个东西」，现在问「这个东西由哪些模块构成、哪些可以少写一遍」。三份 receipt 仍 `healthy: true`，**不修改编译器产出的 Markdown / HTML**（禁止 post-process），本文件即为偏差记录与后续追踪入口。

## 7. 非目标（本阶段）

- 不做总体产品方案 / 技术方案、不定架构、不写 PRD、不实现代码、不安装任何项目；
- 不把「多个类似项目」简化成「挑一个最优项目」；
- 不因热度、README 声明或模块名字面相同就推断模块构成与工作量；
- 不自动 commit / push，等 zj 显式触发（当前 `docs/`、`.workbuddy/` 仍未跟踪）。
